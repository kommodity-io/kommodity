# Upgrading to kommodity-cluster 0.40.0

Version 0.40.0 adds **per-pool Azure image selection**: a nodepool (or the
control plane) may now override the Talos boot image that its
`AzureMachineTemplate` renders, closing the gap with the other providers
(Hetzner, Scaleway, KubeVirt already honored pool-level image overrides).

## What changed and why

Previously the Azure worker and control-plane machine templates read **only**
the global `talos.*` image settings. Any pool-level `talos.imageName` was
silently ignored at render time — even though the template-name hash already
keyed off it, so a pool setting it got a new template name that still booted
the global image (a misleading half-support). GPU pools that requested a GPU
image therefore booted the base `kommodity-talos-azure` image, and the NVIDIA
kernel-module/runtime machine-config patches alone do not change the boot
image.

Now `kommodity.azure.image` merges the pool's `talos` block over the global
one — per key, pool wins — and the template-name hash uses the same merged
block, so hash and rendered image always agree.

## Values interface

Nothing moves; the change is purely additive:

```yaml
talos:
  imageName: kommodity-talos-azure-v1.14.2   # global default

kommodity:
  nodepools:
    gpu:
      sku: Standard_NC24ads_A100_v4
      talos:
        imageName: kommodity-talos-azure-gpu-v1.14.2   # per-pool override
```

- Any image key can be overridden per pool — `imageName`, `id`,
  `computeGallery`, `marketplace` — with the usual precedence within the pool
  (`marketplace` > `computeGallery` > `id` > `imageName`). A pool-level
  `imageName` still reuses the global
  `kommodity.provider.azure.subscriptionID`/`talosImageResourceGroup` to build
  its ARM ID.
- Precedence consequence: a pool's `imageName` does **not** beat a
  globally-set `talos.computeGallery`/`marketplace`/`id` (per-key merge, not
  per-block replace). Pools overriding `imageName` should only do so when the
  global block also uses `imageName`.
- Pools without a `talos` block are unaffected and render byte-identical to
  0.39.x.

## Upgrade impact

- **Clusters that never set a pool-level `talos` block:** no visible change —
  rendered manifests and template names are identical to 0.39.x. Verify with a
  `helm template` diff, which should come back empty.
- **Clusters that already set a pool-level `talos` block:** the pool's
  rendered image is now part of the template-name hash — unconditionally, not
  only when it differs from the global image. For a pool whose image was
  previously ignored this rolls the template name (and replaces the pool's
  machines with the intended image). For a pool whose block happens to match
  the global one the name also changes once on upgrade: hashing it
  unconditionally is what makes future same-version identity changes (e.g.
  both blocks renaming a gallery together) roll the name instead of trying to
  mutate the same-named immutable `AzureMachineTemplate`.
- **Same-version identity changes:** overriding a gallery name or marketplace
  publisher/offer/SKU at the same version (invisible to the pre-0.40 identity
  hash) rolls the template name too.
- **Unrenderable-but-unused global image:** with every pool overridden, the
  global `talos.imageName` may lack its `subscriptionID`/`talosImageResourceGroup`
  without breaking the render — hash evaluation only renders pool images.
